# Prueba 2 — Transaccionalidad

Demostrar con un escenario real por qué resolver la transaccionalidad en infraestructura (sin que `CustomerService`
dependa de Spring) sigue garantizando atomicidad, comparando el comportamiento con y sin el decorador transaccional
activo.

---

## 🔄 Escenario de prueba

A diferencia de un caso con dos escrituras (como un depósito, que actualiza una cuenta y registra una transacción),
`CreateCustomerUseCase` realiza una única operación de persistencia:

```
1. Guardar el cliente nuevo (INSERT en customers)
```

Aunque solo hay un `save()`, el problema de atomicidad que `@Transactional` resuelve sigue existiendo: si algo falla
**después** de guardar pero **antes** de que la operación termine de responder, sin transacción el cliente queda
persistido en la base de datos aunque la API responda con un error — un **"dato fantasma"**, inconsistente desde la
perspectiva de quien consume la API, que no tiene forma de saber que la creación sí ocurrió.

## ⚠️ Preparación

En `CustomerService`, dentro del método `execute(CreateCustomerCommand command)`, agrega esta línea entre el
`save(...)` del cliente y el `return` final:

```java

@RequiredArgsConstructor
public class CustomerService implements GetAllCustomersUseCase, GetCustomerByCodeUseCase, CreateCustomerUseCase,
        UpdateCustomerUseCase, DeleteCustomerUseCase {

    // CREATE
    // =========================================================
    @Override
    public CustomerResponse execute(CreateCustomerCommand command) {
        if (this.customerRepositoryPort.existsByDocumentNumber(command.documentNumber())) {
            throw new CustomerAlreadyExistsException("número de documento", command.documentNumber());
        }

        if (this.customerRepositoryPort.existsByEmail(command.email())) {
            throw new CustomerAlreadyExistsException("email", command.email());
        }

        String customerCode = this.customerApplicationHelper.generateCustomerCode();
        Customer customer = Customer.create(
                customerCode,
                command.documentNumber(),
                command.documentType(),
                command.firstName(),
                command.lastName(),
                command.email(),
                command.phone()
        );
        Customer savedCustomer = this.customerRepositoryPort.save(customer);

        // ⚠️ LÍNEA TEMPORAL PARA LA PRUEBA — simula un error después de persistir
        if (true) throw new RuntimeException("Error simulado después del save()");
        //---------------------------------------------------------------------

        return this.customerApplicationMapper.toResponse(savedCustomer);
    }
}
```

> 💡 **Nota importante:** a diferencia de `AccountService` (donde comentábamos `@Transactional` directamente en esa
> misma clase, por tratarse del enfoque pragmático), aquí `CustomerService` **nunca tuvo** esa anotación — vive en
> `TransactionalCustomerServiceDecorator`. Por eso, para los dos escenarios que siguen, lo que se comenta/descomenta
> no es nada dentro de `CustomerService`, sino la forma en que el decorador participa en el flujo.

## 🧪 Escenario A — SIN transacción (desactivando el Decorator)

### Paso 1: Comenta temporalmente `@Primary` y `@Component` en el Decorator

Para simular el escenario sin transaccionalidad, necesitamos que `CustomerController` reciba el `CustomerService`
puro en lugar de `TransactionalCustomerServiceDecorator`.

Comentamos primero `@Primary`:

```java

@RequiredArgsConstructor
//@Primary  ← comentado temporalmente
@Component
public class TransactionalCustomerServiceDecorator implements
        GetAllCustomersUseCase, GetCustomerByCodeUseCase, CreateCustomerUseCase,
        UpdateCustomerUseCase, DeleteCustomerUseCase {
    // ... sin cambios en el resto de la clase
}
```

> ⚠️ **Importante**: al comentar únicamente `@Primary`, ahora existen **dos beans** sin desambiguar para las mismas
> cinco interfaces (`CustomerService` y `TransactionalCustomerServiceDecorator`). Esto hará que la aplicación **falle
> al arrancar** con `NoUniqueBeanDefinitionException`, porque Spring no puede decidir cuál inyectar en
> `CustomerController`.

Para evitar ese error de arranque y lograr que el controlador use específicamente el `CustomerService` puro (sin
transacción), comentamos también el `@Component` del decorador, para que ese bean ni siquiera se registre en el
contenedor:

```java

@RequiredArgsConstructor
//@Primary
//@Component  ← comentado temporalmente, para que Spring ni siquiera lo registre
public class TransactionalCustomerServiceDecorator implements
        GetAllCustomersUseCase, GetCustomerByCodeUseCase, CreateCustomerUseCase,
        UpdateCustomerUseCase, DeleteCustomerUseCase {
    // ... sin cambios en el resto de la clase
}
```

Con `@Component` comentado, `TransactionalCustomerServiceDecorator` deja de existir como bean, y `CustomerService`
queda como la única implementación disponible de las cinco interfaces — exactamente lo que necesitamos para probar
el comportamiento **sin** transacción.

## 🎓 Conclusión de la prueba

Este escenario confirma el objetivo central de todo el proyecto: aunque `CustomerService` **nunca** supo que existía
`@Transactional`, el comportamiento transaccional observado es idéntico al que tendríamos si la anotación estuviera
puesta directamente en el servicio (como en `banking-account-service`). La atomicidad no depende de *dónde* viva la
anotación dentro del código, sino de que *algún* punto de infraestructura abra y cierre correctamente la transacción
alrededor de la operación completa — en este caso, `TransactionalCustomerServiceDecorator`, manteniendo intacta la
pureza de application.
